# Replacement manuscript text — Dataset and attack taxonomy (Revision 1.1)

## Attack Dataset and Test-Case Curation

The revised corpus is maintained as a single self-contained JSON file, `attacks/ipi_dataset.json` (dataset version 2.1.0). The source collection contained 390 records. We first consolidated 25 exact-payload aliases and then merged 17 additional records that expressed the same attack objective and operative action with only wording-level variation or redundant explanation. The resulting active corpus contains 348 test cases, with 97 BHV (scan-objective manipulation), 92 SEC (security-check manipulation), 83 INFO (synthetic-context disclosure request), and 76 TOOL (tool-action manipulation) cases. No cases were added solely to increase the corpus size. All 390 historical source identifiers remain traceable within the JSON provenance and exclusion records, while only the 348 curated test cases are eligible for execution.

A high-similarity screening step identified 28 candidate pairs. Similarity scores were used to prioritize review rather than as an automatic deletion criterion. Twenty-four candidates corresponded to the plain/obfuscated comparison design and were retained as paired experimental conditions. Four other highlighted pairs were consolidated as semantic redundancies. After curation, a pairwise lexical screen compared the remaining unpaired test cases after Unicode NFKC normalization; no non-paired candidate exceeded a character-sequence ratio of 0.82 or a token Jaccard similarity of 0.72. This screen is a reproducible similarity check, not proof that all semantic overlap has been eliminated. The final corpus contains 30 matched plain/obfuscated pairs (30 plain controls and 30 obfuscated treatments). Each obfuscated member was reconstructed as a deterministic, character-level transformation of its designated plain control. This reconstruction holds the base wording, category, intended action, and prompt-framing annotation constant within a pair while varying the declared transformation. The transformation recipes and pair identifiers are embedded in the JSON dataset. Consequently, the obfuscated prompts in version 2.1.0 should be treated as a revised, controlled treatment set rather than assumed to be byte-identical to the historical OBF payloads.

The five historical payload-design labels (BASE, EXTENDED, ADV, SE, and OBF) are retained as provenance metadata only. They do not form a single ordinal scale of attack sophistication: some labels described construction variants, whereas others described rhetorical framing or text transformation.

## Prompt-Framing Annotation and Obfuscation

Prompt framing is represented separately from both the attack objective and character-level obfuscation. Each test case records (i) `instruction_forms`, describing the surface form of the instruction (imperative/directive, polite request, interrogative request, persona assignment, or declarative pretext/claim); and (ii) a multi-label set of `framing_devices`, which may include authority claims, procedural-update pretexts, compliance/audit pretexts, technical/debugging pretexts, performance/resource pretexts, urgency, politeness/cooperation appeals, social proof/consensus, persona or mode reassignment, false-completion claims, waiver/exemption claims, safety/ethics appeals, and research/measurement pretexts. The dataset records the normalized lexical cues that triggered each framing label, together with the versioned matching rules. Generic terms such as “policy,” “pipeline,” or “metrics” are not sufficient by themselves to trigger a framing-device label. For each obfuscated treatment, framing is inherited from its matched plain control because the treatment applies character-level transformations without changing the underlying wording.

Obfuscation is encoded independently through an `obfuscation` object that records whether a transformation was applied, its technique codes and names, and the recipe version. The techniques include Unicode homoglyph and Cyrillic-lookalike substitution, leetspeak substitution, zero-width character insertion, Persian half-space insertion, soft-hyphen insertion, full-width character substitution, and deterministic misspelling.

Framing labels were generated using a rule-assisted lexical procedure by a single curator. They are accompanied by matched-cue evidence but have not been independently adjudicated, and no inter-annotator agreement has been measured. They should therefore be interpreted as descriptive annotations rather than validated measurements of psychological persuasion or causal factors. Future work should conduct blinded independent annotation and report agreement before using these labels for confirmatory comparisons.

## Injection Delivery Point

The supplied implementation writes each payload to `target/lab_content.txt` and renders it in the User Review paragraph on the `/page` target route. The historical `source_type` and L1/L2 labels are retained only as provenance metadata; the implementation does not instantiate separate L1 and L2 delivery conditions. HTML-attribute injection, hidden-HTML injection, and JavaScript-based injection are not evaluated by this version of the testbed.

## Reproducibility Note

All run-level results must identify dataset version 2.1.0 and the exact model/provider configuration. Previously reported results obtained from the original 390-record corpus must not be pooled with results from this revised corpus: the active test set has been deduplicated, and the obfuscated treatment prompts have been reconstructed as controlled matched variants. The earlier experiment logs were not included with the supplied project files, so the historical percentages cannot be recalculated from those logs at present.
